# 数据治理专家 × KN Chat 交互方案

> 目标：让「数据治理专家」主动找到每个僵尸表/问题表的负责人（真实调用者），通过 KN Chat 与负责人直接交互，完成「确认保留 / 申请下线 / 归档」等治理动作，全程在记录群留痕、回答落库。
>
> 状态：方案设计稿（2026-09）

---

## 一、一句话回答：用户能和数据治理专家互动吗？

**能。** KN Chat 机器人 API 兼容 Telegram Bot API，天然支持双向交互：

- **专家 → 用户**：`sendMessage` 主动推送（@负责人 + 通知内容）
- **用户 → 专家**：`getUpdates` long polling 接收用户消息（文本命令 / 群内@ / 私聊 / 回复），专家解析后 `sendMessage` 回复
- **记录群**：所有推送和回答同步转发到指定 KN Chat 群，形成可审计的留痕

完整支持的命令式交互、群内 @、私聊回复、回复指定消息；按钮（callback）需额外确认（见第五节）。

## 三、核心流程

### 3.1 发现问题表（已有能力，复用）

扫描各层（ods/dwd/dws/ads）零访问表、延迟表、备份表、分桶不合理表——这些是治理对象。输出 `问题表清单`。

### 3.2 定位负责人（核心，用「按账号搜索用户」）

对每张问题表，从 SR 审计日志找**最近的真实业务调用者**：

```sql
SELECT user, COUNT(*) AS n, MAX(timestamp) AS last_ts
FROM starrocks_audit_db__.starrocks_audit_tbl__
WHERE timestamp >= DATE_SUB(CURRENT_TIMESTAMP(), INTERVAL 90 DAY)
  AND (
    stmt LIKE '%ods_app_hold_apply%'      -- 命中该表
  )
  AND user NOT LIKE 'e\_%'                 -- 排除系统账号
  AND user NOT IN ('root','admin','backup_user','bigdata')
  AND NOT (
    lower(stmt) LIKE 'desc%'               -- 排除表结构查询
    OR lower(stmt) LIKE 'show%'
    OR lower(stmt) LIKE 'explain%'
    OR stmt LIKE '%information_schema%'
  )
GROUP BY user ORDER BY last_ts DESC
```

**负责人判定：所有真实业务调用者全发**（用户已确认）。

### 3.3 账号 → 用户（无映射，直接按账号搜）

`employee` 表就是账号索引（已验证：`u_zhangyong` → 张勇 `zhangyong@kn.group`）：

```sql
SELECT name, email FROM employee
WHERE lower(user) IN ('u_qilonghuang', 'qilonghuang')
   OR lower(userId) = 'qilonghuang'
   OR lower(substring_index(email,'@',1)) = 'qilonghuang'
```

### 3.4 通知 + 交互

```
resolveUserId(email) → user_id
sendMessage(chat_id=user_id, text=通知, mention=@负责人)
```

通知内容模板：

```
📋 数据治理提醒
表: ods_app_hold_apply
问题: 零访问（90天无业务查询）/ 数据停更 1756 天
源业务库: app_catalog.coconut.hold_apply
您最近 90 天访问过此表，请确认处理:
- 回复: 保留此表
- 回复: 申请下线此表（将生成 DROP 草稿）
- 回复: 此表不属于我
```

## 四、交互方式设计

### 4.1 命令式交互（推荐先做，无需平台确认）

| 用户输入 | 含义 | 专家动作 |
|---|---|---|
| `/start` | 初始化 | 返回使用说明 |
| `/help` | 帮助 | 返回所有命令说明 |
| `/status` | 状态 | 返回当前待处理表清单 |
| `/my` | 我的表 | 列出用户负责的所有问题表 |
| `/保留 <表名>` | 确认保留 | 更新台账状态=保留，通知记录群 |
| `/下线 <表名>` | 申请下线 | 更新台账=待审批，生成 DROP 草稿，通知记录群 |
| `/归档 <表名>` | 申请归档 | 更新台账=归档，通知记录群 |
| `/不在我 <表名>` | 拒绝归属 | 记录，不再发给该用户 |
| 自由提问 | 如"这表为什么下线" | 专家结合元数据/血缘用 AI 回复 |

### 4.2 按钮式交互（需平台确认 callback 可用）

`sendMessage.reply_markup.inline_keyboard` 带「✅保留 / 🗑下线 / 📋详情」按钮。**前提**：需联系 KN Chat 平台维护者确认 callback 回调可用（文档明确要求）。若确认可用则体验最佳（点一下即可）。

### 4.3 Mention 指定用户

通知发到记录群时，用 `knchat://user?id=<user_id>` 实现 @负责人，确保用户被真正提醒：

```
<a href="knchat://user?id=1571267420">@黄启龙</a> 您负责的表 ods_app_hold_apply 请确认处理
```

## 五、记录群机制

| 项目 | 说明 |
|---|---|
| 记录群类型 | KN Chat 群（supergroup），机器人入群 |
| 群配置 | 需允许机器人入群（`Allow Groups`）、关闭 `Group Privacy`（否则收不到普通文本） |
| 记录内容 | ① 每条发送给用户的通知 ② 用户每次回答 ③ 状态变更 |
| 记录格式 | 时间 + 用户 + 表名 + 动作，群内留痕可审计 |
| 群 chat_id | 建群后机器人入群，`getUpdates` 读取或 BotFather 获取 |

记录群消息示例：

```
[2026-09-08 14:30] → 通知 u_qilonghuang: ods_app_hold_apply 待确认
[2026-09-08 15:02] ← u_qilonghuang: /保留 ods_app_hold_apply
[2026-09-08 15:02] → 状态更新: ods_app_hold_apply = 保留
```

## 六、存储架构（两层：MySQL 权威 + 记录群留痕）

> 已确认：**不接入 Langfuse**。交互结果以 MySQL 台账为权威存储，发送/回答留痕以 KN Chat 记录群为准，AI 推理过程不额外落库。

```
┌─────────────────────────────────────────────┐
│ 记录群（KN Chat 群）—— 展示层/留痕             │
│ · 每条通知 / 用户回答 / 状态变更 → 实时转发     │
│ · 给人看：审计、争议追溯、团队同步              │
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│ 治理台账（MySQL）—— 存储层/权威                │
│ · gov_notify_log: 每条通知（表/人/状态/时间）   │
│ · gov_action_log: 每个处理动作（保留/下线/归档） │
│ · 群消息可刷屏丢失，数据库才是唯一权威           │
└─────────────────────────────────────────────┘
```

### 6.1 治理台账表设计

```sql
-- 通知记录
CREATE TABLE gov_notify_log (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  table_name VARCHAR(255) NOT NULL,      -- 问题表
  user_account VARCHAR(64),              -- SR账号 u_xxx
  user_name VARCHAR(64),                 -- 姓名
  email VARCHAR(128),                    -- 邮箱
  kn_chat_user_id BIGINT,                -- KN Chat user_id
  notify_type VARCHAR(16),               -- ZOMBIE/DELAY/BACKUP/...
  status VARCHAR(16),                    -- PENDING/CONFIRMED/REJECTED/ARCHIVED
  sent_at DATETIME,
  replied_at DATETIME,
  reply_text VARCHAR(255)
);

-- 处理动作记录
CREATE TABLE gov_action_log (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  table_name VARCHAR(255),
  action VARCHAR(16),                   -- KEEP/DROP/ARCHIVE/REJECT
  actor_account VARCHAR(64),
  actor_name VARCHAR(64),
  created_at DATETIME,
  detail TEXT
);
```
